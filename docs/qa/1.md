# TradieHunter — Fix Plan from Manual Testing

**Repo:** `johnverz22/tradiehunter` · **Probed:** `main` @ `02f7d6b` (no `dev` branch exists on the remote; only `main`, `feat/admin-user-detail`, `fix/e2e-findings`)
**Flow under test:** job flow v2 (pay at completion), direct request → tradie accept → Booked
**Method:** static read of backend (`OfferService`, `OffersController`, `OfferTimeoutJob`, `MatchingService`, `JobStatusService`, `ChatHub`, `ChatService`, photo/blob code) and mobile (`tr_home_screen`, `tr_lead_screen`, `ho_matching_screen`, `main.dart` FCM, chat viewmodel, photo viewer). Nothing was run. Items marked **(verify)** need a repro before coding.

**Owner decisions baked in (2026-11-28):** unreachable tradies are hidden (§1); re-contact policy as recommended (§2B); cancellation fee reverses D4 with a recommended formula that is configurable in web admin (§5); full-screen alert platform permissions accepted (§3); photo access is signed and scoped per authorised user, no thumbnails (§4). Section 9 lists what remains open.

Repo rules that shape every fix (from `CLAUDE.md`): status changes only through `IJobStatusService`; v1 and v2 paths must not be mixed; money is `decimal(18,2)`; UI feedback through `THNotice`/`NoticeCopy`; run `docs-sync` after behaviour changes; no secrets in commits.

## 0. Root-cause summary

| # | Symptom | Root cause found |
|---|---|---|
| 1 | Tradie shows "online" from last session | `IsAvailable` is a persisted preference, not presence. Nothing tracks connection, heartbeat or last-seen. Mobile defaults it to `true` when the profile is missing. |
| 2 | Stale offers, conflict toasts, stuck waiting screens | There is **no "withdraw offer" operation**. The homeowner's "Cancel request" cancels the *whole job* and the offer stays `Pending`. When a job leaves `Requested` (booked by someone else, cancelled, expired), sibling offers are never closed or announced. `OfferResponse` has no state for "withdrawn / superseded / job closed". |
| 3 | New request is only a toast | `tr_home_screen` handles `OfferCreated` with `THNotice.info`. No app-root listener, no pending-offer queue, no full-screen route, no sound package. |
| 4 | Photos unreadable (web + tradie) | **Every photo URL is `/api/photos/{blobKey}`, and no such endpoint exists.** The code comment says "in production this would generate a read-SAS". |
| 5 | No cancellation fee | `HandleHomeownerCancellationAsync` computes penalties only for `FlowVersion < 2`. v2 cancels with no money consequence (spec decision D4). |
| 6 | Chat messages missed | Redis presence is per user, never cleared on disconnect (24 h TTL), and an "online" recipient gets **no push**. Pushes are also rate-limited to 1 per 30 s. In-app events reach only users inside the chat group. No OS-level notification when the app is foregrounded (toast only). |

## 1. Online presence for tradies

### Findings
- `TradieProfile.IsAvailable` is set only by `ProfileController`/`ProfileService`. It is used by matching, quick match, board notify and `CreateDirectRequestAsync`, so an offline phone with `IsAvailable = true` still receives requests.
- `JobHub` has no `OnConnected`/`OnDisconnected` presence logic (only `ChatHub` has Redis presence, per job).
- `tr_home_screen`: `online = profile?['isAvailable'] as bool? ?? true`.

### Plan
1. **Split intent from presence.**
   - Keep `IsAvailable` = "I want work" (the broadcast toggle).
   - Add presence = "my app is reachable now": `TradieProfile.LastSeenAtUtc` (migration) plus a Redis key `presence:tradie:{userId}` holding connection ids, refreshed by a heartbeat.
   - **Effective online** = `IsAvailable && (activeConnection || LastSeenAtUtc > now − graceMinutes)`. `graceMinutes` is a platform setting (suggest 2–5 min, owner to confirm).
2. **Backend**
   - `JobHub.OnConnectedAsync/OnDisconnectedAsync` for tradies: add/remove the connection id; on last disconnect write `LastSeenAtUtc`.
   - Hub method `Heartbeat()` (client calls every ~30 s while foregrounded); presence key TTL ≈ 90 s.
   - Introduce `ITradiePresenceService.IsOnlineAsync(userIds)` and use it in `MatchingService` (3 call sites), `OfferService.CreateDirectRequestAsync`, `BoardJobNotifyJob`, and the browse list.
   - Expose `online` + `lastSeenAtUtc` in the tradie list/profile DTOs for the homeowner ("Online now" / "Active 12 min ago"). Never show a made-up value; unknown shows as unavailable (rule 7).
   - Logout: explicit `POST /api/profile/presence/offline` and delete the device token so a logged-out phone stops receiving offers.
   - **Decision: unreachable tradies are hidden, not labelled.** Browse, choose-tradie, quick match and board notify all filter on effective online; a tradie who is `IsAvailable` but past the grace window simply does not appear. The homeowner list may still show a positive "Online now" / "Active N min ago" for those shown.
   - Race case: a tradie drops off between listing and tap → `POST /request` returns 409 `tradie_unreachable`, the mobile client removes the card and shows "That tradie just went offline — pick another".
3. **Mobile**
   - On login/cold start, do **not** trust the cached toggle: show state from the server's effective-online value; offer a "Go online" prompt if `IsAvailable` is true but presence has lapsed.
   - Hub reconnect → send heartbeat immediately. `AppLifecycleState.paused` for > grace → stop heartbeat (server flips to offline on its own).
   - Change the `?? true` default to "unknown/offline".
4. **Admin web:** show online/last-seen on the tradie detail (small, uses same DTO).

### Tests / acceptance
- Unit: effective-online truth table (flag × connection × lastSeen).
- Integration: kill the hub connection → tradie drops out of matching after grace; reconnect → back.
- Manual: log in on a phone, force-close, confirm homeowner no longer sees "Online now".

## 2. Request lifecycle and edge cases (largest item)

### Findings
1. `ho_matching_screen._cancelRequest` calls `cancelJob` (the whole job) and tells the user "the tradie will be told". `HandleHomeownerCancellationAsync` only notifies `MatchedTradieId`, which is null while `Requested`, and **never touches pending offers**. The tradie keeps counting down until `OfferTimeoutJob` fires.
2. Backing out with the system back button does nothing to the offer. The job is `Requested` with a pending offer, so asking another hourly tradie hits `"This job already has a pending request"` → the Conflict toast. Asking the same tradie again hits the `(JobId, TradieId)` unique rule → `"already asked"`.
3. When a job becomes `Booked` (or `Cancelled`/`Expired`), nothing closes the *other* pending offers. Project jobs allow up to 3 concurrent `QuoteRequest` offers, so sibling offers stay on tradie screens; accepting returns `"Job is in state 'Booked'"` → 409.
4. `AcceptOfferAsync` has no atomicity: it reads, checks, saves, then transitions. Two near-simultaneous accepts can both pass the `Pending` check. It also does not check `ExpiresAtUtc`, so an accept after expiry but before Hangfire fires still succeeds.
5. **`OfferTimeoutJob` always calls `SendNextOfferAsync`**, even for `Stage == Direct` v2 offers. That auto-offers to another tradie, or cancels the job with `no_tradie_found`. This contradicts the documented "no auto-broaden on direct requests". **(verify with a test)**
6. `OfferService.DeclineOfferAsync` notifies the homeowner with the **"Offer accepted"** text/event. `OffersController.RespondToOffer` inlines its own decline logic and never calls the service. The two diverge (controller decline does not push to the tradie user group or notify the homeowner by push).
7. Conflict responses use inconsistent bodies (`{ error }` vs `{ message }`, e.g. `JobsController` line 118 vs 305). The client cannot map them, so it shows a generic "conflict" toast.
8. Stale homeowner screens: the request-sent screen reads state on init/reconnect and listens to offer events; if the job is accepted/cancelled by another path it can sit on "waiting". The choose-tradie list still shows "Request" after the job is Booked, so the homeowner can try to contact more tradies. **(verify exact paths)**
9. The post-job form state is not reset when the job is accepted/rejected/cancelled. **(verify provider names in `ho_post_job_*`)**
10. `HandleHomeownerCancellationAsync` sets `job.Status` directly and writes its own history/broadcast, bypassing `IJobStatusService` (violates rule 3).

### Plan
**A. Offer state machine (backend)**
- Extend `OfferResponse`: `Withdrawn` (homeowner pulled it), `Superseded` (another tradie got the job), `JobClosed` (job cancelled/expired). Stored as strings, so no data migration beyond constants; update mobile enum parsing and `OfferEventType` (`withdrawn`, `superseded`, `closed`).
- New `OfferService.WithdrawOfferAsync(jobId, offerId, homeownerId)` + `POST /api/jobs/{id}/offers/{offerId}/withdraw`: validates ownership, deletes the Hangfire timeout, sets `Withdrawn`, leaves the job `Requested`, emits `OfferWithdrawn` to the job group **and** the tradie user group, sends FCM data push so a backgrounded tradie screen clears.
- `IJobStatusService.TransitionAsync`: when a job leaves `Requested` (to Booked / Cancelled / Expired), in the same transaction close every other `Pending` offer (`Superseded` or `JobClosed`), cancel their timeouts, and publish `OfferLifecycleEvent` to each affected tradie. One hook, so no caller can forget it.
- Make `AcceptOfferAsync` atomic: single transaction + optimistic concurrency on `Job` (`xmin` or a row version) or a conditional `ExecuteUpdate` of the offer from `Pending`; reject when `ExpiresAtUtc <= UtcNow`; on loss return a typed 409.
- Fix `OfferTimeoutJob`: only call `SendNextOfferAsync` for non-Direct (quick match) or `FlowVersion < 2`. Direct v2 timeout just closes the offer and notifies both sides.
- Collapse decline into `OfferService.DeclineOfferAsync` (fix the copy/event), called by the controller. Controller keeps only validation/mapping.
- Route homeowner cancel through `IJobStatusService` (or give it a documented, tested hook) so history, SignalR and offer-closing are not duplicated.

**B. Re-contact rules (decided: recommended policy)**
- Keep one pending request per hourly job (existing invariant) and the project cap of 3.
- Make `POST /request` idempotent: same tradie with an existing `Pending` offer returns that offer (200) instead of an error (double-tap safe).
- Relax the `(JobId, TradieId)` unique index to **one `Pending` offer per job+tradie** (filtered unique index). Re-asking is allowed after `Withdrawn` or `TimedOut`; **blocked after `Declined`** (`tradie_already_asked`).
- Choose-tradie list labels past outcomes ("Asked — no response", "Declined") and disables the button for declined tradies; it never fails on tap.

**C. Error contract**
- One response shape for 4xx business errors: `{ code, message }` (RFC 7807-style). Initial codes: `job_not_requestable`, `offer_not_pending`, `offer_expired`, `job_already_booked`, `tradie_unreachable`, `pending_request_exists`, `tradie_already_asked`.
- Mobile `ApiError` reads `code`; `NoticeCopy` maps each to friendly copy and an action (e.g. `job_already_booked` → navigate to booked detail).

**D. Mobile — homeowner**
- Request-sent screen: `PopScope` that asks "Cancel this request to {tradie}?" → calls **withdraw** (not job cancel). Rename actions: "Withdraw request" (offer only) vs "Cancel job" (separate, in job detail).
- Request-sent and choose-tradie screens subscribe to job status + offer events; on `Booked` → replace route with booked detail; on `Cancelled`/`Expired` → clear and leave; on `Declined`/`TimedOut`/`Withdrawn` → back to list with truthful notice. Keep the poll fallback.
- Disable/hide "Request" on every tradie card while a request is pending or the job is not `Requested`.
- Post-job: reset the draft provider on successful submit and whenever the job leaves `Requested`; make it `autoDispose`.

**E. Mobile — tradie**
- All offer events (`expired`, `declined`, `accepted`, `withdrawn`, `superseded`, `closed`) remove the offer from the pending set; `tr_lead_screen` must handle all of them, not just `expired`/`accepted`. On `closed` states show "This request is no longer available" and leave.
- Accept/decline failure with a typed code reconciles against the server then explains why, instead of "may have expired".

### Tests / acceptance
- Backend: withdraw; job booked closes siblings and emits events; two concurrent accepts → exactly one wins; accept after expiry → 409 `offer_expired`; direct v2 timeout does **not** dispatch a new offer or cancel the job; decline sends the right event/copy; double-tap request is idempotent.
- Mobile widget tests: back-press prompts withdraw; booked-by-other clears the tradie offer; homeowner screen leaves "waiting" on Booked/Cancelled.
- E2E (Playwright/Patrol, per `docs/TESTING.md`): two tradies, one project job, A accepts → B's screen clears within the SignalR delay.

## 3. Full-screen incoming request alert

### Findings
`tr_home_screen` handles `onNewJobMatch` and `OfferEventType.created` with a toast. SignalR listeners live in the home widget, so offers arriving while the tradie is on another screen are missed. `pubspec.yaml` has `firebase_messaging` but **no local-notifications or audio package**; the only feedback is `HapticFeedback.lightImpact()` in `th_notice.dart`.

### Plan
1. **`IncomingOfferCoordinator`** (Riverpod notifier at app root, next to `THNoticeHost`):
   - Owns the queue of live offers keyed by `offerId`, fed by (a) hub `OfferCreated`, (b) FCM data messages, (c) cold-start/resume fetch from a new `GET /api/offers/pending/mine` (the current endpoint is per job only).
   - Computes countdown from `ExpiresAtUtc` using a server-clock offset (so device clock drift does not show a wrong timer).
   - Removes offers on any closing event (§2) and when the local timer passes expiry; reconciles on reconnect/resume.
2. **Full-screen route** `/tradie/incoming` (pushed over any screen when the queue becomes non-empty):
   - Card per offer: title, suburb, urgency, rate snapshot, countdown, optional message; "1 of N" pager for concurrent requests, earliest-expiry first.
   - Actions: **Accept**, **Decline**, **View details** (opens the existing `tr_lead_screen` with photos). Single accent action, `THButton`, tokens only (mobile UI rules).
   - Auto-advance to the next offer when the current one resolves; auto-dismiss when the queue empties; expired cards show an "expired" state briefly before removal.
3. **Sound and haptics**
   - Add an audio dependency (or notification-channel sound) and a short looping alert, started when the route shows and stopped on any action/dismiss/expiry. Respect silent mode/DND; always add haptics.
   - Android: high-importance channel `incoming_requests` with custom sound and `fullScreenIntent` (needs `USE_FULL_SCREEN_INTENT`, user-granted on Android 14+); iOS: `time-sensitive` interruption level and a bundled sound.
   - Backend FCM: send offers as high-priority with the channel id and `kind=offer`, `offerId`, `expiresAtUtc` in data. Check `PushNotificationService` for the channel id it sets today **(verify)**.
4. **Decision accepted:** request `USE_FULL_SCREEN_INTENT` (Android 14+) and the iOS time-sensitive interruption level. If the user denies them, degrade to a high-importance heads-up notification with sound, and keep the in-app full-screen alert when the app is open. Declare the permissions with store-review justification ("incoming job requests with a response deadline").
5. Retire the toast for offers (keep `THNotice` for non-offer events).

### Tests / acceptance
- Widget: 3 concurrent offers → pager shows 3; one expires → shows 2; accept one → siblings clear (via §2 events).
- Manual device matrix: foreground, background, terminated, screen locked, silent mode, DND; Android 13/14 permission paths; iOS time-sensitive.

## 4. Job photos not readable (web and tradie)

### Findings
- URLs are generated at four sites as `"/api/photos/{blobKey}"`: `JobsController` upload (≈L281), `AdminService` (≈L824), `AvailableJobsService` (≈L222), `JobService.BuildPhotoUrl` (≈L556). **No controller or `MapGet` serves that route**, so every image 404s.
- Even if added, `<img>` (web) and `Image.network` (mobile) cannot send the Bearer token, so an authenticated endpoint alone would still fail. The web page also uses the relative URL against the web origin.
- `IBlobStorageService.GetReadSasUriAsync` already exists and handles `AzureBlob:ExternalServiceUrl` (needed so phones/emulators reach Azurite).

### Plan (decided: make photos work, scoped to specific users)
1. Add `IPhotoUrlSigner` wrapping `GetReadSasUriAsync` on the photos container. It is called **per request, per viewer**, only after an authorisation check, so a signed URL is only ever issued to someone allowed to see that job's photos. Replace the four relative-URL sites; DTOs return absolute signed URLs.
2. **Who gets photo URLs** (everyone else gets an empty list, never a placeholder):
   - job owner (homeowner);
   - the matched tradie;
   - a tradie holding a `Pending` offer or an open quote request for that job;
   - tradies eligible for the open board, per the existing `AvailableJobsService` rules;
   - staff/admin (web).
   Dispute evidence and credential/receipt containers keep their existing separate rules. Exact-address masking is unchanged.
3. SAS parameters: read-only, single blob, **TTL 30 minutes**; clients re-fetch the job to refresh on 403/expiry (the mobile image `errorBuilder` triggers one refresh and one retry). Not cached or stored in the DB or logs.
4. **Out of scope now:** thumbnails/resizing. Revisit only if the alert card feels slow.
5. Config: set `AzureBlob:ExternalServiceUrl` per environment; CORS on the photos container for the web origin; check the web CSP `img-src`; HTTPS blob host in production (Android blocks cleartext).
6. **Mobile:** `trResolvePhotoUrl` stays but becomes a no-op for absolute URLs; add loading placeholder and retry. **Web:** `JobDetailPage` keeps `<img src>`; add an error fallback.

### Tests / acceptance
- Backend: each role in the list above gets absolute signed URLs; an unrelated tradie, another homeowner and an unauthenticated caller get none; expired SAS returns 403 at the blob host; upload response is signed too.
- Manual: post a job with 3 photos → visible to the homeowner, the offered tradie (alert and detail), and admin web; not visible to a tradie with no offer.

## 5. Cancellation fee for booked / in-progress jobs (v2)

### Findings
- v2 cancels are free by design (`SPECS` D4). The legacy 10 % penalty/refund path applies only to `FlowVersion < 2`.
- v2 final price is determined at completion (`FinalAmount` via `JobMoney.ComputeFinalAmount`); nothing is paid earlier, so a fee must be **billed**, not deducted.
- `PlatformSettings` exists (only quote windows today), with an admin settings page pattern to copy. Payment stays manual (rule 6). `OverduePayment` already blocks posting.

### Decision: D4 is reversed for v2; fee is formula-driven and admin-configurable
**Recommended formula** (all parameters are platform settings; the values below are proposed defaults for you to adjust in admin, not facts about your business):

| Case | Fee |
|---|---|
| `Requested`, or cancelled by the tradie, or reason in the waiver list (`tradie_*`, `scope_change_declined`, `emergency`, `system_failure`, `no_tradie_found`, `dispute_outcome`) | `0` |
| `Booked` and within **grace** (default 30 min after booking) | `0` |
| `Booked` and more than **free-before-start** hours before the scheduled start (default 24 h) | `0` |
| `Booked`, otherwise | `clamp(EstimatedTotal × BookedFeePercent, BookedFeeMin, BookedFeeMax)` — defaults 10 %, $20, $100 |
| `InProgress` | `min( max(hoursWorked, MinBillableHours) × HourlyRate + bookedFee, EstimatedTotal × CapPercent )` — defaults min 1 h, cap 100 % |
| `AwaitingConfirmation` or later | not cancellable: approve or open a dispute |

- `hoursWorked` = elapsed from `StartedAtUtc` to now, rounded up to the next 0.25 h (setting). All amounts `decimal`, rounded to 2 dp (`MidpointRounding.AwayFromZero`) in one pure function `CancellationFeeCalculator` with no clock reads (caller passes `now`), so it is exhaustively unit-testable.
- Fee is capped by the job estimate; if no estimate exists (project quote), use the accepted quote amount; if neither exists, the fee is `0` and staff are notified (never invent a number, rule 7).
- GST treatment of the fee (inclusive vs added) follows the platform's existing GST handling **(verify with accounting before launch)**.
- **Tradie compensation:** `TradieSharePercent` of the fee (default 80 %), remainder to the platform; both configurable. Paid via the existing payout batch once the homeowner's fee payment is verified.

### Settings keys (`PlatformSettingKeys`, each validated with min/max and audited)
`Cancellation.GraceMinutes`, `Cancellation.FreeBeforeStartHours`, `Cancellation.BookedFeePercent`, `Cancellation.BookedFeeMin`, `Cancellation.BookedFeeMax`, `Cancellation.MinBillableHours`, `Cancellation.HoursRounding`, `Cancellation.CapPercentOfEstimate`, `Cancellation.TradieSharePercent`, `Cancellation.WaivedReasonCodes`.

### Web admin
- New **Settings → Cancellation policy** section next to the existing quote settings: editable fields above, inline validation, "Reset to defaults", and **live preview calculator** (enter estimate, hours worked, time to start → shows resulting fee and tradie/platform split).
- `GET/PUT /api/admin/settings/cancellation` reusing `PlatformSettingsService.UpsertAsync`; every change writes an `AuditLog` entry (who, old → new). Role: SuperAdmin only (verify against existing admin roles).
- Admin job detail shows the fee breakdown and status; cancellations list gets a fee column and a "waive fee" action (reason required, audited, staff-only).
- Follow the web design rules (tokens only, one `btn-accent` per view).

### Server-determined amount and flow
1. `GET /api/jobs/{id}/cancellation-quote` → `{ fee, breakdown[], waived, waiverReason?, policySnapshotId }`.
2. `POST /cancel` carries `acknowledgedFee`; if it no longer matches (time moved, policy changed) → 409 `cancellation_fee_changed` with the new quote.
3. **Policy snapshot at booking:** the terms in force when the job is booked are stamped on the job (like `FlowVersion`), so a later admin change never alters a booked job's terms; the quote uses the snapshot. Terms are shown on the request-sent/booked screens before the homeowner commits.
4. Cancel runs through `IJobStatusService` → `Cancelled`; a `CancellationFee` record (`decimal(18,2)`, breakdown JSON, status, due date, `JobId`, policy snapshot id) is created; the homeowner gets the existing manual-payment instructions; staff verify the receipt. Unpaid past due → existing `OverduePayment` flag and posting block. No `Refund` rows for v2.
5. Tradie sees "Cancelled — compensation $X pending" and the amount appears in earnings once verified.

### Mobile
Cancel sheet shows the quote (breakdown and "why"), requires an explicit confirm, handles `cancellation_fee_changed` by re-showing the new amount. `THNotice` + `NoticeCopy`; no `$0.00` placeholders. Gate on `FlowVersion >= 2`; v1 refund logic untouched (rule 5).

### Docs
Record the reversal in `docs/MVP.md`, update `docs/SPECS.md` (cancellation/money, remove "non-monetary only" in D4 and §4 transition row), then run `docs-sync`.

### Tests / acceptance
- Unit: calculator table (each case above, boundaries at grace/24 h, rounding, cap, missing estimate, waived codes).
- Integration: cancel Booked → fee row, notification, admin visibility; stale `acknowledgedFee` → 409; admin changes a setting → new jobs use it, already-booked jobs keep their snapshot; v1 job unchanged.
- Web: settings validation, audit entry, preview matches the calculator.

## 6. Chat reliability and native notifications

### Findings (chat)
1. `ChatHub.SetOnlineAsync` adds the **user** to `chat:online:{jobId}` on `JoinJob` and removes on `LeaveJob`. `OnDisconnectedAsync` does not clear it, so after a kill/network loss the user stays "online" up to 24 h. `ChatService.SendChatPushAsync` then **skips the push** for that recipient — later messages are never delivered anywhere.
2. Presence is per user, not per connection: two devices/tabs, or a stale `LeaveJob` from one, corrupt the flag.
3. Push rate limit "1 per 30 s per job+recipient" silently drops the second and later messages with no collapse/summary.
4. Real-time delivery only reaches users in the `chat-{jobId}` group; a recipient on another screen gets no live unread update (only push, which #1 suppresses).
5. Client side looks reasonable (re-join + reconcile on reconnect, dedupe by id) but the send path (`_hubReady`, failed/optimistic rows, retry) needs a repro. **(verify)**

### Findings (notifications)
`main.dart` `_handleForegroundMessage` adds to the in-app inbox and shows `THNotice.push` only; there is no local-notification plugin, so nothing reaches the OS notification shade while foregrounded, and no channel/permission fallback logic beyond the initial `requestPermission`.

### Plan
**Chat backend**
- Presence per **connection**: Redis hash `chat:conn:{connectionId} → {userId, jobIds}` plus `chat:online:{jobId}` as a counted/sorted set with short TTL refreshed by client ping (60–90 s). `OnDisconnectedAsync` removes the connection and decrements; user is online only while ≥ 1 live connection is in the group.
- Never suppress a push solely on the presence flag if the last heartbeat is stale.
- Replace the hard rate limit with FCM **collapse key / notification tag** per job so messages update one notification instead of being dropped; include unread count.
- Also send a user-level hub event (`ChatMessageReceived` to `Clients.User(recipient)`) so inbox badges/unread update outside the chat screen.
- Server returns an ack with the persisted id; the client treats the optimistic row as sent only on ack.

**Chat mobile**
- Outbox with retry/backoff for failed sends; surface "failed — tap to retry"; re-join group and reconcile on resume and reconnect (partly present).
- Join/leave on screen enter/exit and on `AppLifecycleState` changes.

**Native notifications (all notification types: chat, offers, job status)**
- Add `flutter_local_notifications` with Android channels (`chat`, `incoming_requests`, `job_updates`) and iOS foreground presentation options (`setForegroundNotificationPresentationOptions`).
- Foreground: show an OS notification (heads-up) instead of the in-app toast; background/terminated: FCM notification payload as today; tap routes via `routeForMessage`.
- Permission handling: Android 13+ `POST_NOTIFICATIONS`, iOS authorization; if denied or the channel is disabled, **fall back to `THNotice`** and show a one-time settings nudge.
- On logout unregister the FCM token **(verify it is removed today)** so a shared device never shows the previous user's notifications.

### Tests / acceptance
- Backend: kill connection → recipient gets push on next message; two connections for one user; burst of 5 messages → collapsed notification with correct count.
- Manual: A/B send 10 messages alternately with app foreground/background/killed on the recipient; airplane-mode toggle; notification permission denied → toast fallback.
